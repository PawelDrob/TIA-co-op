# HMI screens, tag tables, text lists

The guides: wincc-comfort-openness.md; for screen objects, wincc-screen-objects.md.

`<clone>` is the folder that holds `.claude`, and `<py>` is `<clone>\.venv\Scripts\python.exe -X utf8`.

## The middle

1. **Generate.** Export a template screen as the reference. Write the generator in the repo's `gen\` with `<clone>\TiaHmiGenerator\hmixml.py`: `begin`, `plan` for anything not yet in TIA, `add`, `finish`. It writes `hmi\generated\`, or with several HMI devices `hmi\<device>\generated\` by `begin(repo, device=...)` and `--device` on every command. It validates and rolls back on errors. Done when `finish` passes.
2. **Look.** The `hmipreview` commands run from `<clone>\TiaHmiGenerator`. A change of only tag tables needs no server, as the preview draws no tag table. Otherwise look in the running records first: each file in `%LOCALAPPDATA%\hmipreview\running` holds a server's `url`, and one whose `<url>api/about` answers with this repo in `repo` is this repo's: use it, as it shows the documents as they are now. Without one: `<py> -m hmipreview serve <repo> --detach`, which prints the URL once the server answers (on this machine only; `--host 0.0.0.0` opens it to another). A `serve --detach` that prints `preview server did not start` names its log; `cannot listen on` there means another server holds the port: add `--port 0`, and it prints the port it got. Then `png <repo> <name> <out.png>` and look at the picture, and `diff <repo> <name>` for the run summary, each with `--kind popup` or `--kind template` for a pop-up or template. From `<clone>`, the change report TIA against generated: `<py> TiaChangeReports --git <repo> HEAD --after-set generated --only hmi -o <page>`. What each of them shows: wincc-comfort-openness.md, 3. Workflow, step 3. Done when you have looked at every document the change imports in the preview, a tag table or text list in the change report.
3. **Stop for the user's yes.** Every HMI import waits for it, into the user's TIA and into a trial alike. Unless the change is of tag tables only, fetch the URL (`curl.exe -s -o NUL -w "%{http_code}" <url>`) in a command of its own, after `serve` has returned: an agent's command runner can end the server with the command. Then end your turn on one message: the preview URL, the change report, what goes into TIA in its order (a `delete` of each existing tag table first, as an import cannot replace one), and for anything new to this project the trial offer (Imports that can end TIA). When you hand the user a `serve` command (the two cases below), write it out for a terminal of their own: the `serve` command for this repo (the one you ran, if you ran one), without `--detach`, with real paths: `cd <clone>\TiaHmiGenerator`, then `<clone>\.venv\Scripts\python.exe -X utf8 -m hmipreview serve <repo>` with your options; it runs only from that folder. If the URL did not answer, give that `serve` command in place of the URL. If it answered but `serve` printed a note that the server may end with the command, give the URL, and that `serve` command for when the URL stops answering. Either way, tell the user to open the URL their terminal prints. A change of only tag tables gives the change report in place of the URL, and the rest of the message as for any change. Done when your turn has ended on that message.
4. **Import,** after the user's yes to that message, by the rule below: the `delete` of each existing tag table it replaces, then tag tables, text lists and templates, then pop-ups and screens. A change after the yes to what goes into TIA (a document generated again, a refusal fixed, a trial's finding) goes back to step 2 and stops again. A new screen, pop-up or template goes to the folder its path under `generated\<kind>\` mirrors, a screen into `zzStaging` only when the user asks for it or for a faceplate's staging screen (What goes by hand). A tag table is built with `hmixml.tag_table`, not by hand, and imports from `hmi\generated\tags\`: a tag whose `Length` does not fit its data type ends TIA, as an `Int` tag cloned from a `Bool` one with `Length` 1 did. Done when every item is ok.
5. **Clean up.** A screen you imported only to try something goes with `delete`, then a `zzStaging` left empty with `delete_folder`; what the user asked to keep stays. Done when nothing you made for yourself is left in the project.
6. `compile(hmi)`. Done with 0 errors.

## Imports that can end TIA

A refused HMI import can throw `NonRecoverableException`, and TIA then closes, taking unsaved edits with it.

- **Built only from objects this project holds or an earlier import here accepted:** in the user's TIA, after `tia_status`; if `unsavedChanges`, ask the user to save first.
- **Anything new to this project:** tell the user the risk and offer a trial, in the message of step 3. With a yes to the trial: `background_open` on the session archive in the repo's `archives\` with `write: true` and a new `repo` for each trial. Copy the repo's whole `hmi\` into the trial's repo, as an import takes screens from the bound repo only and the validator reads the reference exports there, and import there. `background_close` with `discard: true`, then `connect` and import in the user's TIA; tell the user the trial's repo at `<projects root>\<repo>` and its project at `<projects root>\_bridge\retrieved\<repo>` stay, for them to delete. Without a trial, import directly if the user says so.

## What goes by hand

- A screen with an alarm view or a system diagnostics view: the export leaves those out, so a re-import deletes them. List it in `hmi\handbuilt.json`, and change it in TIA.
- Faceplate types: their contents do not go through Openness. Generate a staging screen into `zzStaging`; the user builds the type.
