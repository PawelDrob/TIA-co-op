## 2. HMI (WinCC Comfort)

| What | Behaviour | Source |
|---|---|---|
| Objects | Screens, templates, global screen, pop-ups, slide-ins, tag tables, text and graphic lists, VB scripts, cycles, connections, as SimaticML | [12] |
| Not exportable | Among others: alarm view, alarm indicator, alarm window, trend views, table and value views, recipe view, system diagnostics view/window, screen window, HTML browser, media player, camera, PDF view, status/force, editable text field, list/combo box, check box, option buttons, scroll bar, connector, pipes. The export leaves them out without a message, so an `Override` import of that screen deletes them `[EXPORT]` `[INFERRED]` | [21] |
| Screen attributes | A screen offers only `Name` through the object model: number and template come from the export `[PROBE]`. `GetAttribute('Number')` throws: *'get_Number' is not supported by type 'Siemens.Engineering.Hmi.Screen.Screen'.* An export without defaults (`ExportOptions.None`) takes 20 to 30 ms a screen, a full one up to 2 s, and leaves out number 1, the default `[PROBE]` | [33] |
| Screen numbers | Unique on the device. A new screen, or an `Override` of one, whose number another screen has ends TIA: `NonRecoverableException`, *The "screen number '1' for screen 'Connection status' is not unique for this device.* `[PROBE]`. An `Override` takes the document's number, and the old one is free after it. A document without `Number` gets the lowest number no other screen has, new or over an existing screen, so an export without defaults does not carry number 1 back `[PROBE]`. TiaBridge refuses a taken number before TIA sees the file | |
| Templates and pop-ups | No number: a pop-up's `Number` is refused, and TIA keeps running (*The 'Number' attribute at the 'Siemens.Engineering.Hmi.Screen.ScreenPopup' object ... is not supported.*). Names are kept apart per kind: a new pop-up or template with a screen's name goes in, and so does a new screen with a template's name `[PROBE]` | |
| Import order | With function keys: global screen, then templates, then screens (readme) | [8] |
| Cycles | `CycleComposition.Import` with `Override` takes back a full export (`WithDefaults` + `WithReadOnly`) unchanged: all 19 cycles of the test project, every one a system object (`Default cycle 1` to `5` too), in one call. An edited `CycleTime` lands, and a file of a new name makes a cycle with `IsSystemObject` false. An export without defaults (`ExportOptions.None`) leaves out `StartAtStartingPoint` when it is true, its default, and TIA imports such a file as false: all 19 changed so. An HMI tag keeps its acquisition cycle after an import over every cycle, the time of its cycle changed too: tags naming `1 s` and a new cycle, made for the probe in a table of internal tags, which TIA took with an `AcquisitionCycle` link `[PROBE]`. A delete was not tried. TiaBridge exports cycles full and refuses a cycle document that is no full export or lacks `StartAtStartingPoint` (validator rule `cycle.not-full`) | |
| Slide-ins and global screens | A slide-in goes back through `ScreenSlideinFolder.ScreenSlideins.Import`, the global elements through `HmiTarget.ImportScreenGlobalElements` and the screen overview through `HmiTarget.ImportScreenOverview`, each with `Override`. The full exports of the four slide-ins of the test project and of the overview went back identically. In slide-in `Top` an added text field (copied from a screen) and `Dimension` 267 to 300 landed and then round tripped identically, IDs renumbered by TIA; the overview's `Height` 0 to 60 landed. The global elements' `BackColor` lands. After an import their export no longer writes the empty layer 0 it wrote before (the layer still counts 1); from then on they round trip identically. A text field in the global elements ended TIA: `NonRecoverableException`, *Cannot create the 'Hmi.Screen.TextField' object ... The HmiScreenItemData object is not allowed in screen Global screen.* Other items there were not tried. Without `Override` TIA refuses an existing slide-in (*... the identifier(s) 'SlideinType'.*) and the overview (*An instance of the object already exists into the 'ScreenOverview' composition.*). The HMI compiled with 0 errors after the edits. A field at `Top` 384 in a slide-in of `Dimension` 300 made the compile warn *The position or size of the object is invalid.*; at `Top` 100 the slide-in compiled without a warning (2026-11-12 and 2026-11-19) `[PROBE]`. That an `Override` drops what the export cannot carry, as on a screen, is `[INFERRED]`. A new slide-in or global screen and a delete were not tried. TiaBridge imports both kinds from their export folders over the device's own only, the global screens only with `override` passed true, and refuses global elements holding a screen item and one listed in `handbuilt.json` before TIA sees them | |
| Graphics and graphic lists | A project graphic exports (`WithDefaults`) as `<name>.xml` naming its image by a path relative to it, `<DefaultImageStream external="path"><name> files\DefaultImageStream.png</DefaultImageStream>`, the image written into that folder. `MultiLingualGraphicComposition.Import` with `Override` takes it back identically with its image; a replaced PNG lands, and a new graphic from its `.xml` and folder lands as written. A graphic list linking that graphic exports the same after an import over the graphic. A graphic list goes in new from a file through `GraphicListComposition.Import`, each entry linking a graphic by name (`<LinkList><Picture TargetID="@OpenLink"><Name>Home</Name></Picture></LinkList>`), and its full export (`WithDefaults` + `WithReadOnly`) round trips identically; the minimal export TiaBridge writes unless `options.full` holds only the values that differ from the defaults, and imported over the list it leaves the full export identical, entries with non-default values too (`FlashingEnabled`, `FlashingRate`, `UseTransparentColor` with `TransparentColor`, `UseFlashTransparentColor` with `FlashTransparentColor`, an `EntryType` `Range`) and the list's comment; a changed and an added entry land. `Content`, `Graphic`, `Image` and `GraphicContent` in an entry are refused with TIA running: *The '...' attribute at the '...GraphicListEntry' object ... is not supported.* An entry naming a graphic the project lacks imports without a word, keeps the name, and the HMI compile then fails: *A graphic is missing in graphics list '...'. If a standard graphic is defined, this will be used. Otherwise, an empty graphic will be used.* An entry naming `home` links the graphic `Home`, and the export writes `Home`. A graphic I/O field links its graphic list as `<LinkList><PictureList TargetID="@OpenLink"><Name>...</Name></PictureList></LinkList>`, the property name in TIA's `Data\Hmi\IDoc\Settings_Screen.xml` (`GraphicList`, `GraphicsList`, `Graphiclist`, `List` and `Graphics` are *not supported*). A screen with such a field stays identical through an import of the list over itself, one with a changed entry and an import of a graphic it shows, and the HMI compiles clean. A graphic document naming no image imports as a graphic with no image (2026-11-12 and 2026-11-17) `[PROBE]`. A delete was not tried. TiaBridge refuses a graphic whose image is not beside it or that names none, and a graphic list naming a graphic the project does not have (matched without case, as TIA links it), before TIA sees them | |
| VB scripts | `VBScriptComposition.Import` with `Override` takes a new script from a file with `Code`, `PreCode` and `Type` (`ScriptCode` is *not supported*), into the folder whose composition it is called on, and adds a line end to `Code` on the first import; after that the round trip is identical. The minimal export (`ExportOptions.None`) leaves out `PreCode` and `Type` when they hold their defaults (two line ends, `Sub`); imported over the script it leaves the full export identical, a `Function` with a `PreCode` and a comment too. An edited line lands. A screen event calls a script as `<Hmi.Event.FunctionListEntry>` with `Name` the script and `Type` `VBScript`; the call tried had no parameters `[PROBE]`. TIA's enum `FunctionListEntryTypes` holds `None`, `VBScript`, `CScript`, `SystemFunction` (by reflection of its `Siemens.Simatic.Hmi.Global.dll`). A screen whose button calls the script exports the same after an edited script is imported over it, and the HMI compiles clean. A script with a syntax error (an `If` without `End If`) imports without a word; the HMI compile then reports 0 errors while nothing calls it, and fails once a screen calls it: *Function ... compiled with errors. Compile the function in the editor to obtain detailed information.* (2026-11-12 and 2026-11-19) `[PROBE]`. Scripts with parameters, callers other than a screen button, and a delete were not tried. TiaBridge imports the kind, refuses a document of another class, and refuses a delete | |
| Faceplate instances | Import and export inside the screen; object name and type name are mandatory; an unknown type, event or interface attribute aborts the import [22]. A type version missing from the project library crashed TIA `[IMPORT]`; grouped instances are refused `[IMPORT]` | [22] |
| Faceplate types | Contents do not export or import: `Export` writes version metadata only, `ExportAsDocuments` refuses every format `[PROBE]`. Putting one in work with `Edit(LibraryTypeInstanceInfo)` ended TIA (`NonRecoverableException`) `[PROBE]`. A person builds the type in TIA | |
| SimaticML written by a script | TIA refused a tag table declaring `encoding="utf-8-sig"` `[IMPORT]`; TiaBridge refuses any declared encoding other than `utf-8`, in every SimaticML. Section 1, Editing an OB's SimaticML | |
| HMI tag tables | `Override` on an existing table deletes it first; it closed TIA once `[IMPORT]`, so TiaBridge refuses it. Broken tags block the export `[EXPORT]` | |
| Alarms, recipes, logs, user administration | No objects in the V20 API (enums only): nothing to create, export or import [33] | [33] |
| Styles | Objects with a style export the values stored before the style was switched on; toggle `UseDesignColorSchema` (off, export, on, export) to get the style values (readme) | [8] |
